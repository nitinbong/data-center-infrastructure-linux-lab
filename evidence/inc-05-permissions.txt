--- 3e. Walk every component of the path ---

[web01]$ namei -l /srv/webcontent/index.html
f: /srv/webcontent/index.html
drwxr-xr-x root root      /
drwxr-xr-x root root      srv
drwx--S--- root root      webcontent
-rw-rw-r-- root webadmins index.html
FINDING: /srv/webcontent is 0700 root:root. www-data is neither the owner nor in the
group, so 'other' applies and other has no permissions at all - it cannot
even traverse (x) into the directory, let alone read (r) the file.

########## 4. TRIAGE - part B: the editor who cannot write ##########

[web01]$ ls -l /srv/webcontent/notice.html
-rw-r-----+ 1 deploy deploy 28 Sep  6 23:57 /srv/webcontent/notice.html

[web01]$ id webdev
uid=1003(webdev) gid=1007(webdev) groups=1007(webdev),1002(webadmins)
FINDING: notice.html is 0640 deploy:deploy. webdev is in 'webadmins', not
in 'deploy', so again only 'other' applies - and other has no write bit.
The file was created without the shared group because it was chowned away
from the SGID-inherited group.

########## 5. FIX ##########
5a. restore the document root to the documented state

[web01]$ ls -ld /srv/webcontent
drwxrwsr-x+ 2 root webadmins 4096 Sep  6 23:57 /srv/webcontent

5b. put the published file back under the shared group

[web01]$ ls -l /srv/webcontent/notice.html
-rw-rw-r--+ 1 deploy webadmins 28 Sep  6 23:57 /srv/webcontent/notice.html

NOT the fix: chmod -R 777 /srv/webcontent
That would let every local account - including unprivileged service
accounts - rewrite the served content, which turns a 403 into a defacement
vector. The correct fix is group membership plus the SGID bit.
