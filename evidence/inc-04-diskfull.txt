########## 5. THE TRAP - deleting the log frees nothing ##########
The obvious next step is to delete the large log file:

[web01]$ ls -lh /srv/data/logs/app.log
-rw-r--r-- 1 root devops 120M Sep  6 23:57 /srv/data/logs/app.log

[web01]$ rm -f /srv/data/logs/app.log

[web01]$ du -sh /srv/data
36K	/srv/data

[web01]$ df -h /srv/data
Filesystem      Size  Used Avail Use% Mounted on
/dev/loop1      224M  121M   86M  59% /srv/data

PROBLEM: du now reports almost nothing, but df still reports the space as
used. du walks directory entries; df asks the filesystem. When a file is
unlinked while a process still holds it open, the directory entry is gone
but the inode and its blocks are not released until the last descriptor
closes. du cannot see it; df can.

########## 6. FIND THE PROCESS HOLDING THE DELETED FILE ##########
--- 6a. Scan /proc for deleted files still held open ---

[web01]$ for p in /proc/[0-9]*; do ls -l $p/fd 2>/dev/null | grep deleted; done
  pid=2192  l-wx------ 1 root root 64 Sep  6 23:57 3 -> /srv/data/logs/app.log (deleted)

--- 6b. lsof is not installed; on a production host:  lsof +L1  ---
        (lists open files with a link count of 0 = deleted but held)

--- 6c. Identify the holder before acting on it ---

[web01]$ ps -o pid,ppid,user,etime,rss,cmd -p 2192

########## 7. RECLAIM THE SPACE ##########
Two safe options: truncate the descriptor in place (keeps the process
running), or restart the process so it closes the descriptor.

Option A - truncate through the descriptor, no restart required:
  descriptor: /proc/2192/fd/3
